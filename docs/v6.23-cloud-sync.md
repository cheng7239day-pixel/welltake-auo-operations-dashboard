## 雲端行為與權限

1. 管理者先匯入完整 Raw 並按「上傳目前 Raw」，確認檔案、資料日期、筆數及 Site。
2. 同一交易按 Site 保存不可變版本。只有所有廠區均有權限且所有案件驗證通過才完成。
3. 最新依「資料日期 → 上傳時間 → ID」排序，補傳舊日期不取代較新現況。
4. 已核准使用者登入後自動載入授權廠區；每 60 秒及頁面重新取得可見狀態時檢查更新。
5. 檢視歷史或本機待上傳資料時，不自動切走；可手動回到雲端最新。
6. Viewer 僅讀取；Leader 僅上傳與讀取授權廠區；Admin 可管理。未登入、待審核、停用帳號不得取得正式資料。
7. 新增帳號預設待審核。只有管理者可指定已有正式基準的 Site，無法在頁面提升為 Admin。
8. 雲端回傳案件只留在記憶體；登出或讀取權限失敗移除雲端畫面，保留本機資料。已下載或先前看過的資訊無法遠端回收。
9. 登入使用 PKCE magic link，同一瀏覽器開啟郵件連結。寄信速率受專案郵件服務限制。

## 最小上傳欄位

案件編號、Site、承辦人／群組、Request Type、狀態、建立／處理／關閉／到期日期、分類與案件類型。**不接受問題描述、聯絡人、電話、信箱等額外欄位。** 另保存原檔名與上傳者 ID 作稽核。客戶案件編號、承辦人與檔名仍屬內部資訊，需公司核准的雲端資料用途與存取人員。

## 套用與驗收步驟（已獲核准）

1. 執行 `004_raw_cloud.sql`：新增兩張啟用 RLS 的表與五個對 authenticated 開放的 RPC；表格不開放直接讀寫，RPC 每次重新驗證帳號與 Site。
2. 執行 `005_raw_cloud_tests.sql`：交易內使用合成帳號／案件，最後 ROLLBACK，不保留測試紀錄。
3. 在 Supabase Auth URL Configuration 新增精確 redirect：`https://cheng7239day-pixel.github.io/welltake-auo-operations-dashboard/`。保留既有 cloud-test redirect；不開啟 wildcard。
4. 將 `index.html`、`dashboard-repair.js`、`cloud-sync.js` 一起發布至 GitHub Pages。SQL 與測試檔僅供維運，不是前端必要檔案。
5. 管理者於主平台登入；用公司核准的合成檔案先完成兩個日期的上傳、重新登入、另一個瀏覽器讀取、Viewer／Leader 廠區隔離檢查。
6. 確認後才上傳正式客戶資料。不應將真實 Raw 或救援備份加入公開 GitHub。

## 回復方式

前端可回復到上述基準 commit。新的雲端表格和歷史資料保留；不要 DROP TABLE。停用新 RPC 的 EXECUTE 可停止新同步；若有既存頁面已讀取資料，需同時讓使用者關閉／登出。
